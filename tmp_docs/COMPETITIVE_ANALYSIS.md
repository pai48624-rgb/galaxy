# 경쟁 앱 비교 분석 및 개선 계획 (COMPETITIVE_ANALYSIS.md)

2026년 9월 기준 구글 플레이스토어에 등록된 국내 상위 로또 번호 생성 앱 7개를 실제로
조사(웹서치)해서, 우리 앱과 기능을 대조하고 무엇을 받아들이고 무엇을 의도적으로
안 받아들이는지 판단 근거를 남깁니다.

## 1. 조사한 앱과 핵심 기능

| 앱 | 핵심 특징 |
|---|---|
| 로또퍼스트 | 28가지 통계 분석(회귀, 베이지안, 클러스터링, 엔트로피, 카이제곱 등) |
| 로또 번호 생성기(김성종) | QR 자동 등록, 구글드라이브 백업, 판매점 위치 |
| 로또 번호 생성기 & 통계 | 홀짝/구간/연속수 방지 밸런스 로직, 가볍고 개인정보 미수집 |
| 로또 번호 생성기(제이리) | 랜덤/핫/콜드 3모드, **포함/제외 번호 지정(최대 5개)**, 합계·홀짝·고저 비율, 생성 히스토리, 공유 |
| 로또번호 자동생성 | 반자동(고정번호+임의생성), 출현/미출현 통계 |

## 3. 의도적으로 채택하지 않은 기능과 그 이유

**28종 "고급 통계"(회귀분석, 베이지안, 클러스터링, 카이제곱검정, 엔트로피 등)와
AI(LSTM) 예측**은 로또퍼스트·LottoZone 같은 앱의 핵심 마케팅 포인트지만 채택하지
않았습니다. 이유:

1. 로또는 매 회차 완전 독립시행이라, 과거 데이터에 아무리 정교한 통계 기법(회귀분석,
   베이지안 추론, LSTM 딥러닝 등)을 적용해도 **다음 회차 예측력은 수학적으로 0**입니다.
   이 프로젝트의 일관된 원칙(README §5, §6에 이미 명시)과 정면으로 배치됩니다.
2. 이런 기능은 "그럴듯해 보이는 복잡함"으로 다운로드를 유도하는 마케팅 장치에 가깝고,
   실제로는 사용자에게 "확률이 올라간다"는 잘못된 인상을 줄 위험이 있습니다.
3. 대신 우리는 **있는 그대로의 사실**(빈도, 미출현 기간, 궁합수, 방금 뽑은 조합의 합계/
   홀짝비율 같은 객관적 서술)만 제공하고, 매 화면에 "확률에 영향 없음" 고지를 유지합니다.

**판매점 위치 검색**과 **클라우드 백업**은 유용해 보이지만 이번 라운드에서는
보류했습니다 — 위치 검색은 지도 API 연동과 별도 요금제 문제가, 클라우드 백업은
사용자 인증(로그인) 체계가 선행되어야 해서 지금 아키텍처(로그인 없는 로컬 SQLite
단일 사용자 앱)를 벗어나는 더 큰 작업입니다. 필요하시면 별도 라운드로 설계하겠습니다.

## 4. 이번에 실제로 추가한 기능

### 4-1. 포함/제외 번호 지정
- `algorithm.py`: `pure_random_pick(include, exclude)`, `weighted_pick(strategy, include, exclude)`,
  `sample_unique_weighted(weights, k, include, exclude)`, `validate_constraints(include, exclude)`
- `app.py`: `/api/generate`가 `include=1,7,20` / `exclude=3,4` 쿼리 파라미터를 받음
- `generate.html`: "⚙️ 포함/제외 번호 지정하기" 접이식 패널, **클라이언트 사전검증으로
  잘못된 입력 시 무료 생성 횟수를 낭비하지 않도록 처리**
- 검증 규칙: 포함 최대 6개, 포함/제외 중복 불가, 제외 후 남은 후보가 6개 미만이면 거부

### 4-2. 조합 밸런스 통계
- `algorithm.compute_balance_stats(numbers)`: 합계, 홀짝 개수, 고저(1~22/23~45) 개수,
  AC값(산술적 복잡도 — 모든 번호쌍 차이값 중 서로 다른 값의 개수 - 5, 0~10 범위)
- `/api/generate` 응답에 `balance` 필드로 포함
- 화면에 "합계 149 · 홀3:짝3 · 저3:고3 · AC값 10" 형태로 표시
- **이건 예측이 아니라 방금 뽑힌 조합의 객관적 서술**이라는 점을 유지 — "이 조합이 좋다/
  나쁘다"는 평가는 하지 않습니다.

두 기능 모두 실제 단위테스트(algorithm.py 13개 신규) + E2E 테스트(3개 신규)로 검증
완료했습니다(TEST_RESULTS.md 참고).

## 5. 이번 라운드에서 자체 점검한 "내가 놓쳤을 수 있는 함정"

사용자 요청("니가 짠 플랜의 오점이나 함정, 무시한 수정사항을 비교 검증")에 따라
DESIGN.md와 지금까지의 작업을 스스로 재검토해서 찾은 항목입니다.

| 항목 | 문제 | 조치 |
|---|---|---|
| CSS/JS 로딩 실패 시 무방비 | tailwind.css가 어떤 이유로든 로딩 실패하면 화면 전체가 스타일 없는 상태로 방치되고, 사용자는 원인을 알 수 없었음 | 최소 안전망 인라인 CSS + 로딩 실패 자동 감지 배너 추가(base.html), E2E 테스트 2건 추가 |
| 포함/제외 기능의 검증 실패가 무료 횟수를 낭비할 뻔함 | 서버 검증 실패(400) 이전에 이미 `guardGenerate()`로 카운트가 소모되는 구조였다면 사용자에게 불이익 | 클라이언트 사전검증을 `guardGenerate()` 호출보다 먼저 수행하도록 순서를 설계, 테스트로 고정(`test_generate_page_validates_before_wasting_free_quota`) |
| `sample_unique_weighted`가 무한루프에 빠질 가능성 | 후보 풀이 소진됐는데 목표 개수(k)에 못 미치면 예전 코드는 `while True`로 무한 반복할 수 있었음 | `while len(picked) < k and candidates:` 로 후보 소진 시 루프 종료하도록 수정 (이번 리팩토링에 포함됨) |
| 문서(DESIGN/TEST_PLAN)가 코드와 따로 놀 위험 | 기능을 고칠 때마다 문서 업데이트를 깜빡할 수 있음 | `test_design_doc_api_table_matches_actual_routes`로 최소한 API 경로 목록은 자동 대조 |
| 경쟁 앱 대비 실질 기능 격차를 자체적으로는 인지 못함 | 내부 논리만으로는 "무엇이 부족한지" 판단 근거가 없었음 | 이번 문서(COMPETITIVE_ANALYSIS.md)로 외부 벤치마크를 최초로 도입, 이후 기능 추가 시 이 표를 갱신하는 걸 관례로 삼기를 권장 |
